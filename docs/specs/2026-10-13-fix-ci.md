# fix-ci: make a pull request's red checks green

Date: 2026-10-13 · Branch: `jpcasa/fix-ci-skill-85ccf2` · Ships as `/real-skills:fix-ci`, plugin `0.13.0`

## Goal

Add `/real-skills:fix-ci`: take a pull request whose checks are red, read each failed job, say what kind of failure it is, reproduce the ones a code change can fix, fix them, prove the failing command now passes, push one commit after a yes, and stay with the pull request until CI is green or three rounds are spent. A script reads the checks and logs, cuts each failure down to what matters, classifies it, runs the commands, checks the fix for shortcuts, builds the commit, pushes and watches. The agent reads the failure and writes the fix.

It sits beside `solve-merge-conflicts` and `review-prs`: three things that stop a pull request, one skill each.

## Decisions taken (asked 2026-10-13)

- **Write scope:** one push per round to the pull request branch, after a yes. Refused on a moved head, a closed pull request or a fork. `--no-push` stops at the commit and prints the command.
- **Loop:** after the push a `watch` command waits for the new CI run. Red again: the next round starts on the new failures, with a new yes for its push. It stops at green, at three rounds, or when a failure the round before claimed to fix is red again.
- **Failures code cannot fix:** every failed job gets a class. Runner and network failures, and failures that pass locally on the same commit, are offered a rerun, made only after a yes. Missing secrets, permissions and checks from other services are reported with their evidence and never touched.
- **Workspace:** the user's checkout when it is on the pull request branch, clean and at the pull request head (dependencies are already there). Otherwise a worktree of its own at that head.

## Assumed (say so if wrong)

- **Pull requests only, one per run.** A red run on `main` with no pull request is out of scope for v1.
- **GitHub Actions is the only CI whose logs are read.** Every other check (Vercel, a status from another app) is `external`: named, linked, not read.
- **The main thread fixes.** No new agent.
- **A fix that makes a check pass by weakening it is asked, one question each** (list in section 6). It is never refused outright: a test that is wrong because the pull request changed behaviour on purpose is a real case.
- **The repo's other checks are not run locally.** The push runs all of CI; the next round catches what the fix broke. The local proof is only that the commands that were red are green.
- **Jev: shadow.** Three questions, logged, deciding nothing until `/calibrate` switches one on.

## Non-goals

- Fork pull requests, CI hosts other than GitHub Actions, several pull requests in one run, branch runs without a pull request.
- Rebase, force-push, merging, approving, commenting on or closing the pull request.
- Conflicts with the base. A conflicting pull request is told to run `/real-skills:solve-merge-conflicts` first.
- Reproducing a step that writes somewhere (deploy, publish, migrate, upload). Never run locally.
- Fixing a job that is also red on the base branch, unless the user says to (asked once at the start).
- New behaviour. The fix is the smallest change that removes the cause of the failure.

## Approach

### 1. Commands

```
/real-skills:fix-ci [<pr>] [--no-push] [--worktree]
/real-skills:fix-ci status
/real-skills:fix-ci drop <run-id>
```

- `<pr>`: a number or a URL. Left out: the pull request of the current branch; if it has none, the user's open pull requests with a failed check are offered and one is asked for, never picked.
- `--worktree`: use a worktree even when the checkout would do.
- `status`: runs that are not finished, with their round and verdict. `drop`: ends a run and removes its worktree, if it has one. Changes left in the user's checkout are theirs and stay.

### 2. Flow

```
start (pull request · head · every check) ──► all green ──► stop
        │                                └──► nothing failed yet, some running ──► watch
        ▼
failures: one per cause, each with class, command, errors, excerpt
        │
        ├── external · config ──► reported, never touched
        ├── infra ──► rerun offered
        ▼
repro: each code failure's command, at the head, before any edit
        │        └── green here ──► not reproduced ──► rerun offered
        ▼
fix (the agent edits the workspace) ──► check: edits listed · shortcuts asked · red commands green · commit
        │
        ▼
summary in chat ──► YES ──► push ──► watch ──► green ──► done
                                        └──► red ──► next round (max 3)
```

When a round has something to push, nothing is rerun: the push runs every check again. A rerun is offered only when a round has nothing to push.

### 3. What `start` reads, and what it hands over

Measured on echo1 #2945: one failed shard's log is 1,592 lines and 247 KB, and `gh run view --log-failed` labels every line `UNKNOWN STEP`. The failure itself is three annotations and one command. So the script reads, and the agent gets the cut.

Per failed check on the pull request head:

- From the check rollup: name, workflow, conclusion, run id and job id (from the details URL). No Actions URL: `external`.
- `repos/{slug}/actions/jobs/{id}/logs`: the job's log, saved whole in the run folder, colour codes stripped.
- `repos/{slug}/check-runs/{id}/annotations`: file, line, title, message. The one GitHub adds for the exit code is dropped.
- `command`: the last `##[group]Run …` block before the first `##[error]` line, up to its `shell:` line. It is the command as the runner ran it, expressions already filled in. No YAML is parsed.
- `errors`: the annotations; without any, the `##[error]` lines.
- `excerpt`: at most 60 lines around the first errors. `log` is the path of the whole file, for when the agent needs more.
- `signature`: the command and the error titles with numbers, durations and hashes removed. Failed jobs with one signature (matrix legs, shards) are one failure with several `jobs`.
- `also_red_on_base`: the same job failed on the base branch's latest finished run of that workflow.
- `passed_before`: the same job passed in an earlier attempt on this same commit.

### 4. Classes

First match wins. Every class carries its `evidence`: the line or the fact that decided it.

| Class | Decided by | What happens |
|---|---|---|
| `external` | The check is not a GitHub Actions job | Reported with its link |
| `derived` | Its only error is the exit code, its command is not one that runs here unasked, and another job in the same run failed with errors of its own (a job that sums up others) | Not counted, not fixed: it follows the others |
| `infra` | Conclusion `timed_out`, `cancelled` or `startup_failure`, or the error lines match the runner and network table (lost runner, no space left, `ECONNRESET`, registry 5xx, rate limit, an action that failed to download) | Rerun offered |
| `config` | The error lines match the secrets and permissions table (`Resource not accessible by integration`, `Input required and not supplied`, bad credentials, an empty secret) | Reported: a person with access has to fix it |
| `code` | Everything else | Reproduced, fixed, proven |

A `code` failure also gets a `repro`:

| `repro` | When | Meaning |
|---|---|---|
| `run` | `.claude/fix-ci.json` maps the job to a command, or the logged command is one line of known tools joined by `&&` (package-manager scripts, test runners, type-checkers, linters, formatters, builds) and neither it nor the package script it names contains a write word | The script runs it |
| `ask` | Any other shape: several lines, a pipe, `make`, a tool not on the list | Shown in full; run only after a yes for that command |
| `never` | A write word (`deploy`, `publish`, `release`, `push`, `apply`, `migrate`, `upload`, `terraform`, `kubectl`, `aws`, `gcloud`, `vercel`, `docker push`, `gh … create/merge`), or the failed step is an action, not a command | Never run here. Fixed from the log, reported as not proven |

### 5. `repro`: is it red here too?

`repro --run <id>` runs every `run` command in the workspace at the head, before any edit (it refuses when the workspace differs from the head). In a worktree the install command runs first. Each result is compared with what CI said:

| Result | Means | Then |
|---|---|---|
| `reproduced` | Red, and its output names a file or an error line CI named | The failure to fix. This command must be green at `check` |
| `not_reproduced` | Green here on the same commit | Nothing to fix here: rerun offered |
| `differs` | Red, and nothing in its output matches CI (a missing tool, a wrong directory, an environment CI has and this machine lacks) | Said with its tail. The fix cannot be proven here: `fixed_unverified`. The answer names `repro` in the config |
| `not_run` | `ask` not yet answered, or `never` | The same |

While fixing, the agent runs whatever is fastest (one test file). The proof is the script's run of the whole command.

### 6. `check`: the fix, checked

The agent edits files in the workspace with its own tools, then sends `{ subject, edits: [{ file, why, failure }] }`.

1. **Listed.** What git says changed (tracked and untracked) must be exactly the list. Each `failure` is a `code` failure of this round.
2. **Shortcuts.** Each hit is one question for the user, answered with `decide --id <flag> --confirmed`. An edit made after the answer needs a new one.

| Flag | Hit when the fix |
|---|---|
| `ci_config` | Changes a file under `.github/` or another CI's config |
| `check_config` | Changes a lint, type-check, format or test-runner config (built-in names plus `check_config` globs) |
| `test_removed` | Deletes a test file, or leaves one with fewer test cases than it had |
| `test_skipped` | Adds a skip or focus marker (`.skip`, `.only`, `xit`, `@pytest.mark.skip`, `t.Skip`, `#[ignore]`, `@Disabled`) |
| `test_edited` | Edits a test file a failure names. Right when the pull request changed behaviour on purpose; that is the user's call |
| `suppression` | Adds `@ts-ignore`, `@ts-expect-error`, `@ts-nocheck`, `eslint-disable`, `biome-ignore`, `# type: ignore`, `# noqa`, `//nolint` or `as any` |
| `snapshot` | Changes a snapshot file |
| `dependencies` | Changes a package manifest's dependencies or a lockfile |
| `large` | Touches more than 10 files or 300 lines (`max_files`, `max_lines`) |

3. **Proof.** Every `reproduced` command runs again on the fixed tree. Green: fixed. Red: `still_red`, with the tail.
4. **Commit.** Built with a temporary index and `git commit-tree` on the head: the subject the agent sent (72 characters at most), then one line per edit. No hook runs and HEAD does not move until the push.

| Verdict | From | Means |
|---|---|---|
| `nothing_to_fix` | `start` | Every check is green, or there are none |
| `ci_running` | `start` | Nothing failed yet and some checks are running |
| `fixable` | `start` | At least one `code` failure |
| `rerun_offered` | `start`, `repro` | What is left is `infra` or `not_reproduced` |
| `report_only` | `start` | What is left is `external` or `config` |
| `fixed` | `check` | Every reproduced command is green, every flag answered |
| `fixed_unverified` | `check` | The same, and at least one fixed failure could not be proven here. Said in those words before the push |
| `needs_decision` | `check` | An unlisted edit, an open flag, an `ask` command |
| `still_red` | `check` | A reproduced command is still red. Nothing is pushed |
| `blocked` | any | A gate blocks |
| `pushed` | `push` | The commit is on the branch |
| `green`, `red`, `pending`, `timed_out` | `watch` | What CI says about the pushed commit |
| `stuck`, `gave_up` | `watch` | Red with failures the last round claimed to fix; or three rounds spent |

### 7. Gates

| Gate | Blocks when |
|---|---|
| `pr_open` | The pull request is closed or merged |
| `same_repo` | The head branch lives in a fork |
| `conflicts` | The pull request conflicts with its base: CI may not be running on what would merge. Names `/real-skills:solve-merge-conflicts` |
| `ci_pending` | Never blocks. Some checks are still running while others failed: said, because more may fail |
| `red_on_base` | Never blocks. Failures also red on the base are left out unless the user says to fix them here |
| `local_unpushed` | Never blocks. The local branch has commits the pull request lacks: a worktree is used, and CI's head is what gets fixed |
| `head_unchanged` (`repro`, `check`, `push`) | The pull request head is no longer the commit this round read. The round is over; `start` again |
| `listed`, `flags`, `proof` (`push`) | Any is not satisfied |

A gate that could not be read is `unknown`, never `pass`.

### 8. The writes

Two, each after its own yes in the conversation:

- `push --run <id> --confirmed`: `git push <remote> <commit>:refs/heads/<head>`. No force flag exists in the script. Refused when the workspace no longer holds the tree that was checked. Then HEAD is moved to the commit (`git update-ref` with the old value, `git read-tree`): in the user's checkout that moves their branch and leaves it clean; in a worktree it readies the next round. The repo's own pre-push hook runs, as on any push.
- `rerun --run <id> --confirmed`: `gh run rerun --job <id>` for each `infra` and `not_reproduced` job. Once per job per run. Red again after a rerun: it is `code` from then on.

Nothing else: no comment, no review, no merge, no label.

### 9. `watch` and rounds

`watch --run <id>` polls the checks of the pushed commit and returns within eight minutes: `pending` (call again), `green` (the run ends, the worktree is removed), `red` (round + 1, with that round's failures, read as in section 3), or `timed_out` after `watch_timeout_s` in all (default 45 minutes). No check appearing on the new commit within five minutes is said as that: CI did not start.

A new round is a new `repro`, fix, `check`, summary, yes and push. `stuck`: a `code` failure the push claimed to fix is in the new round. `gave_up`: `max_rounds` (default 3) spent. Both stop with what is still red and its excerpts.

### 10. Jev

Three questions, all in `UNCALIBRATED`. Switched on, each can only add a question or an offer; none removes a failure, answers a flag or decides a push.

| Question | Asks | Label | Unsafe side |
|---|---|---|---|
| `failure_is_transient` | Would this failure pass if run again with no change? | Automatic: the rerun's result | `fp` |
| `fix_weakens_check` | Does this edit make the check pass by weakening it? | By hand | `fn` |
| `fix_matches_failure` | Does this edit address this failure? | By hand | `fp` |

Sent: job and step names, the command, one scrubbed error line (300 characters at most), file paths, the agent's one-line `why`. Never code, never the log. Off: `"jev": "off"` in `.claude/fix-ci.json` or `FIX_CI_JEV=off`. Catalog 49 → 52.

### 11. Config and state

`.claude/fix-ci.json`, all optional: `install`, `repro` (`{ "<job glob>": "<command>" | false }`), `ignore` (job globs left out entirely), `check_config` (globs), `max_rounds` (1 to 5), `max_files`, `max_lines`, `gate_timeout_s`, `watch_timeout_s`, `jev`. `install` falls back to `.claude/solve-merge-conflicts.json`, then `dev.install` in `.claude/improve-design.json`. As in `solve-merge-conflicts`, a tracked config file is read as the base branch has it and one the pull request adds is not used.

`~/.claude/state/fix-ci/<run-id>/`: `run.json`, every job log, every command's output. CI logs and other people's code: sensitive, not pruned. `log.jsonl` holds classes, counts, rounds and verdicts, no log text; `jev.jsonl` the cases and labels. Run ids are `ci-<date>-<time>-<hex>`; a worktree is `.claude/worktrees/<run-id>`.

### 12. Changed by the build (2026-10-13)

- **An error that points at a file of the repository is `code`, before any table is read.** A test that expects `401 Unauthorized`, or whose message quotes `ECONNRESET`, would otherwise have been classed as a missing secret or a network error.
- **`derived` is decided by what the script would do with the command**, not by reading it as a shell test: the job reports nothing but its exit code, its command is not one that runs here unasked, and another job of the same workflow run failed with errors of its own.
- **The proof runs before the flags are asked.** A fix that does not work is not worth a question. The proof is kept for the tree it ran on, so answering a flag does not run the command again.
- **`check` takes `leave`**: a failure the agent is not fixing, with one line on why. Without it, every command that was red here must be green, so a half fix cannot be pushed by leaving a failure off the list.
- **A job GitHub already saw pass on the same commit (`passed_before`) is offered a rerun** as well as being fixable.
- **The commit is built from the head plus the listed files only** (a temporary index, `update-index`, `commit-tree`). What a command wrote beside them (coverage, build output) is recorded as the command's and is neither an unlisted edit nor part of the commit.
- **A flag's answer is for one content of the file.** A hash of the flag, the path and the file's content is kept with the yes; the file changed again, the question is asked again.
- **A new `start` for a pull request ends the runs before it** and removes their worktree: one run per pull request at a time.
- **A workspace is made only when there is something the code can fix.** A run that only offers a rerun has none; if the rerun comes back red, the failure is `code` and the workspace is made then.
- **`fix_weakens_check` is labeled by hand.** A yes to a flag means "go on", which is not the same as "this weakens the check" or its opposite.
- **A command never inherits `NODE_TEST_CONTEXT`.** A `node --test` started by the script would otherwise report to a test runner that is not its own. Found by the suite, where the fixture's failing command is `node --test`.
- Config `flaky` lists and the repo's other gates were considered and left out: the rerun and the next round cover both.

From the review of the finished harness, same day:

- **A write word is read as the shell reads the command.** Quotes and backslashes are dropped first (`git pu\sh`), and the long words count anywhere in a word: `scripts/deploy.mjs`, `predeploy`, `db:migrate`. The first version wanted a separator after the word and let `node scripts/deploy.mjs` run.
- **More shapes are asked:** a wrapper that runs something not on the list (`pnpm exec git …`), code given on the command line (`node -e`, `python -c`), a variable set for the command other than a handful that only change output, a package fetched by name (`npm exec`, `bun x`, `pnpm create`), an install or link for the whole machine, a `cd` to an absolute path.
- **A changed package script is asked as `check_config`.** `"test": "vitest run || true"` made the logged command green with no flag.
- **`stuck` is about what the push claimed to fix**, not every failure of the round before. A failure that was left and is still red starts the next round; it does not end the run with "the fix did not work".
- **A new run does not remove an earlier run's worktree when it holds edits nobody pushed.** It is kept and named. `drop` still removes it, and says which files went.
- **A command that runs out of time is killed with its whole process group.** Killing the shell alone left the test runner under it running.
- **Two packages that fail alike are two failures**: the signature keeps the command as it is but for the shard, so `pnpm -F app1 test` and `pnpm -F app2 test` are each proven.
- A job that was rerun shows its old result for a while; rows with the old job id are held back for five minutes at most.
- Not changed: the install command of a worktree runs without a question of its own. It is the user's command, from their config, it is named with the others before anything runs, and it runs the pull request's install scripts, which is the trust the skill states at the start.

## Rejected alternative

Let the agent read `gh run view --log-failed` and fix, with the script only pushing. It is what `do-shit` does today (the last 60 lines of the log) and it is far less code. But the log is the cost: 247 KB for one failed shard, most of it setup, and the last 60 lines of that one are the runner cleaning up. And "it passes now" would be the agent's word. Cutting the log in code is what makes the skill cheap; running the red command before and after is what makes "fixed" a fact.

Also rejected: finding the local command by parsing the workflow file. The harness has no YAML parser and no dependencies, and the log already holds the command with every expression filled in.

## Risks

- **Reproducing runs the pull request's code on this machine, with a command the pull request's own workflow chose.** Forks are refused; only known tool shapes run unasked; anything else is shown first; write words never run. The user's Bash guards do not see commands the script starts. `SKILL.md` says this once, when it names the commands.
- **The write-word list is a net, not a wall.** A package script named `ship` that deploys is caught only if its body says so. `repro: false` for a job in the config is the wall.
- **A fix can be green and wrong.** The flags catch the known shortcuts, not a changed meaning. Every edit is shown before the push, and review is still a separate step.
- **The flags will ask too often**, above all `test_edited` and `as any`. That is the safe direction; `log.jsonl` counts each flag and its answer, to tune from.
- **Local green is not CI green.** That is what `watch` and the rounds are for; `differs` and `fixed_unverified` say so when the local run proves nothing.
- **The class tables are patterns.** A real failure whose log says `ECONNRESET` is classed `infra` and offered a rerun: one wasted CI run, then it is `code`.
- **The command is the last step before the job's first error.** A step that fails under `continue-on-error` writes an error first, so the script would take that step's command, find it green here and offer a rerun for what is a code failure. `repro` in the config names the right command for such a job.
- **A file git ignores is invisible to the check.** A fix that only works because of one is green here, is not in the commit, and is red in CI: the next round says so.
- **Whether GitHub keeps a job's id across a rerun was not checked on a real rerun.** The script does not depend on it either way: old rows are held back for five minutes, then read as they are.
- **First real push and rerun are unverified until someone uses them.** The release note says so.
