# qa-this: QA with checked evidence

Date: 2026-10-08 · Branch: `jpcasa/qa-this-plan` · Ships as `/real-skills:qa-this`, plugin `0.8.0`

## Goal

Add `/real-skills:qa-this`: QA one or more pieces of work (tickets, PRs, a branch, or a described feature) on a non-production environment, with the methods that fit each one, and leave evidence where the team already looks: a short comment on each ticket or PR and one short report file.

The model plans and observes. A script decides which methods run, runs every command itself, computes each item's status from recorded results, and builds the exact text that gets posted.

It sits between `review-prs` and `changelog` in the flow.

## Decisions taken (asked 2026-10-08)

- **Jev:** shadow first. Code rules pick the methods. Jev scores each method per item and is logged; `/real-skills:calibrate` switches a question on per machine.
- **New tests:** written into the working tree, test files only, never committed. Listed in the report.
- **Database:** a single `SELECT` per check, non-production only. Results leave the machine as counts and column names, never row values.
- **On failure:** the evidence comment plus a bug draft printed in chat. It creates no ticket and moves no status.

## Non-goals

- Production, in any form: no browser, no request, no query.
- Fixing what it finds, editing source files, committing, pushing code, opening PRs.
- Creating tickets, changing status, labels or assignees.
- Load, penetration or cross-browser matrix testing.
- Replacing `do-shit`'s own QA phase. That stays as is; see the rejected alternative.
- Typing credentials. The user signs in; agents never do.

## Approach

### 1. Commands

```
/real-skills:qa-this [<ticket|pr|branch|text>…] [--env <name>] [--method <m>…] [--screenshots] [--no-post]
/real-skills:qa-this setup
/real-skills:qa-this post <run-id> [<item>…]
/real-skills:qa-this outcome <run-id> <item> right|wrong
/real-skills:qa-this stats
```

With no arguments it asks what to QA, and offers what it can see: the current branch's PR, PRs merged in the last 7 days, and tickets sitting in the tracker's QA status. It never picks one silently. At most 10 items per run.

### 2. Flow

1. `start`: resolve each argument to an item, load config, list which methods this session can run and why the others cannot.
2. Per item, the model reads the ticket, the diff and the code, and writes acceptance criteria and proposed checks, following `references/qa-process.md`.
3. `plan`: the script picks methods, checks coverage, applies budgets, refuses production.
4. **One question:** the plan (items, environment, methods, check count), whether using the product may change data on that environment, sign-in if needed, and what gets posted where.
5. Run the checks. The script executes commands and SQL; the `qa-tester` agent drives the browser; the model writes new tests.
6. `status`: the script computes one status per item.
7. `post` (if allowed), then `report`.

### 3. Config: reuse first

Read in this order, never copied: `.claude/qa-this.json`, then `.claude/wtf.json` (tracker, `environments`, `production_hosts`, hosting, runtime), then `.claude/changelog.json` (tracker). `start` returns `needs: ["setup"]` only for what none of them answers. Setup is `probe` plus one question round, and writes only `.claude/qa-this.json`.

```json
{
  "environments": [{ "name": "local", "kind": "local", "base_url": "http://localhost:3000" }],
  "production_hosts": ["app.example.com"],
  "tests": { "unit": "pnpm test --", "e2e": "pnpm playwright test", "globs": ["**/*.test.ts", "e2e/**/*.spec.ts"] },
  "databases": [{ "env": "local", "how": "psql \"$DATABASE_URL\" -At -F '\t'" }],
  "path_rules": [{ "pattern": "^apps/billing/", "methods": ["database"] }],
  "post": "ask",
  "screenshots": false,
  "report_dir": "docs/qa",
  "jev": "shadow"
}
```

`probe` detects test runners and e2e frameworks from dependency names, test globs from existing files, `.claude/launch.json`, and database hints from env var names (names only, never values).

### 4. Methods

| Method | What it does | Chosen by code when | Needs |
|---|---|---|---|
| `checks` | The repo's test and e2e commands, scoped to tests that touch the changed files | Always, when a command is configured | `tests` |
| `browser` | `qa-tester` runs numbered steps in the built-in browser, one screenshot per step | Changed files match UI patterns, or the item has a user-visible criterion | Claude Code, an environment, the plugin's agent |
| `database` | One `SELECT` per check to confirm a write landed or a row has the right shape | Changed files match schema, migration or write-path patterns, or a path rule | `databases` entry for the environment |
| `api` | HTTP requests the plan lists, against the environment's base URL | Changed files match route or handler patterns and no UI covers them | An environment |
| `new_tests` | Writes test files for criteria no existing test covers, then runs them through `checks` | A criterion has no `checks` coverage and `tests.globs` is set | `tests` |
| `runtime` | After the run, reads errors from the configured sources for the run's time window | `runtime` is configured and `browser` or `api` ran | `wtf.json` runtime |

`--method` adds one. A method the session cannot run is listed as `unavailable` with the reason, and any criterion that depended on it is `uncovered`.

Without the built-in browser (Codex, or no pane), `browser` is unavailable. An existing Playwright or Cypress suite still runs through `checks`, and `new_tests` may add a spec to it.

### 5. What good QA means here: `references/qa-process.md`

One page the model follows when it writes criteria and checks:

- Every acceptance criterion is observable and maps to at least one check. No criterion, no QA: ask or mark `blocked`.
- Conditions to consider per criterion: happy path, empty and boundary input, invalid input, permission denied, error and slow states, data actually stored, adjacent flows the diff touched.
- Depth follows risk: money, auth, deletion and migrations get the negative and data checks; a copy change gets one look.
- A check has one action and one observable expected result. "Works" is not a result.
- A pass needs evidence a stranger could re-check: a command and its exit code, a screenshot, a query and its row count, a response status.
- "Not tested" is a result and is reported with its reason.

### 6. The harness: `scripts/qa.mjs`

One JSON object per call. State in `~/.claude/state/qa-this/<run-id>/` (`QA_THIS_STATE_DIR` overrides).

| Command | Decides in code |
|---|---|
| `probe` | Candidates for setup, with the reason for each |
| `start` | What each argument is (`tracker`, `pr`, `branch`, `text`); the diff and changed files for PRs and branches; available methods; `needs` |
| `plan` | Methods per item; that every criterion has a check (`uncovered` otherwise); budgets (30 checks per item, 150 per run); environment allowed or refused; the `qa-tester` prompt files |
| `run` | Executes one `checks`, `api` or `database` check itself and records exit code, status, duration and an output tail. The model never reports these results |
| `tests-open`, `tests-close` | Snapshots `git status` before the model writes tests; afterwards lists every changed path outside `tests.globs` as a violation, and fails the `new_tests` check when there is one |
| `browser-record` | Parses the tester's JSON report; keeps a screenshot only when the file exists inside the item's own folder |
| `runtime-record` | Records the model's reading of the runtime sources (connectors a script cannot reach), marked as reported |
| `block` | Marks an item `blocked` with a reason (sign-in declined, environment down) |
| `status` | One status per item from recorded results |
| `post-plan`, `post-record` | The exact comment per item, and whether posting is allowed; what was actually posted |
| `report` | Writes the report file |
| `outcome`, `stats` | Whether a status turned out right; accuracy per status and method |

**Environment rule** (same as `wtf`'s reproduction rule, same code): kind must be `local`, `preview` or `staging`, and the host must not equal or end with any `production_hosts` entry. With no `production_hosts` configured, every method that touches an environment is refused.

**SQL rule.** `run` accepts a database check only when the statement parses as exactly one `SELECT` (or `WITH … SELECT`), with no semicolon-separated second statement, no `INTO`, no `FOR UPDATE`, and no function from a deny list (`pg_sleep`, `dblink`, `lo_*`, `copy`). It appends `LIMIT 50` when none is present. It records row count and column names. Row values stay in the run folder and are never put in a comment, the report or a Jev request.

**API rule.** `GET` and `HEAD` run as listed. Any other verb runs only on a `local` environment, or on `preview`/`staging` when the user accepted data changes in the plan question.

**Status per item:**

| Status | When |
|---|---|
| `passed` | Every criterion covered, every check passed |
| `failed` | At least one check failed |
| `partial` | Nothing failed, and a criterion is uncovered or a check was skipped |
| `blocked` | Sign-in, environment or access stopped it before any check ran |
| `not_run` | No criteria, or the user dropped the item at the plan question |

### 7. Jev

Five questions, all in `UNCALIBRATED`, each logged as a case record with threshold, direction and unsafe side:

| Question | Would decide | Unsafe side |
|---|---|---|
| `needs_browser_check` | Add `browser` to an item the path rules missed | Saying no |
| `needs_data_check` | Add `database` | Saying no |
| `needs_new_tests` | Add `new_tests` | Saying no |
| `check_covers_criterion` | Reject a check that does not exercise its criterion | Saying yes |
| `failure_is_environmental` | Report a failed check as environment trouble instead of a product failure | Saying yes |

Once switched on, the three `needs_*` questions can only add a method. Jev can never remove one, never turn `failed` into `passed`, and never unlock an environment or a statement.

Sent: item title, criteria lines, changed file paths, one line per check. Scrubbed with the shared redaction library. Never diff or source text, row values, screenshots, URLs with query strings, or credentials. `"jev": "off"` or `QA_THIS_JEV=off` sends nothing.

Labels: `outcome` labels the status-level questions. The plan question labels the `needs_*` questions for free: a method the user adds or removes there is the right answer.

### 8. Evidence

**Where.** A tracker item gets a comment on the ticket. A PR gets a PR comment. A branch or text item has nowhere to post and appears only in the report.

**When.** `post` in config: `ask` (default: the plan question shows the destinations, and the finished comments are shown before sending), `auto` (send without the second look), `off`. `--no-post` forces `off` for one run.

**What.** Built by `post-plan` from recorded results only, at most 12 lines before any screenshot lines, written in full sentences for teammates:

```markdown
**QA: failed** · staging · `9e8d7c6` · 7 of 8 checks passed

- ✅ Export downloads a CSV with one row per order (browser, 3 steps)
- ✅ Row count matches the orders table (database: 42 rows)
- ❌ Empty date range shows an error: the page shows a blank table instead (browser, step 6)
- ⚪ Not tested: email delivery (no mail sink on staging)

New tests, uncommitted: `e2e/orders-export.spec.ts`
Report: `docs/qa/2026-10-08-orders-export.md` · run `qa-…`
```

**Screenshots, opt-in** (`"screenshots": true` or `--screenshots`). Off by default because a screenshot of staging can show customer data and, on GitHub, lands in the repository. When on: failed steps always, plus the last step of each passed criterion, at most 6 per item, through the adapter's **Attach** section. On GitHub that is a push to the orphan `qa-evidence` branch, and the plan question says so.

**Adapters.** `references/trackers/{github,clickup,linear,other}.md`, each with **Fetch**, **Comment** and **Attach**, condensed from `do-shit`'s. GitHub goes through `gh`. ClickUp and Linear go through whatever connector the session has; without one the comment is printed for the user to paste and `post-record` notes `not_posted`.

### 9. The report

`report` writes `<report_dir>/<date>-<slug>.md`, at most 60 lines, uncommitted:

- One table: item, status, checks passed of total, where the evidence was posted.
- Per failed item: the failed checks, expected against actual, and a bug draft (title, repro, expected, actual, evidence).
- Not tested, with reasons. Methods that were unavailable.
- New test files, and that they are uncommitted.
- Environment, commit, run id, and the command to rerun.

The same table is printed in chat with the path.

### 10. Rejected alternative

**Lift `do-shit`'s QA phase out and have both skills share it.** One implementation instead of two. But that phase is wired into `do-shit`'s run state, starts from merged leaf items, knows one method (the browser), and `do-shit` is Claude Code only. Pulling it out changes a calibrated, working harness to serve a skill that does not exist yet. `qa-this` instead reuses the two things that are already separable, the `qa-tester` agent and the environment rule, and `do-shit` can call `qa-this` later if the new skill proves out.

## Risks

- **A pass that is not one.** The unsafe error. Mitigations: the script runs commands and records exit codes itself; a criterion without a check makes the item `partial`, never `passed`; screenshots must exist on disk; Jev cannot improve a status.
- **Changing data on a shared environment.** Using a product creates rows. The plan question says so and names the environment; non-`GET` requests on staging need that answer; `qa-tester` already skips real payments, real messages and deleting non-test data.
- **Production.** Refused in code by host and by kind, and refused outright when `production_hosts` is empty. A database `how` command is the user's own string: setup tells them to point it at a non-production URL, and `run` refuses when the environment it belongs to is not allowed. The script cannot see inside that command, and the skill text and setup say so.
- **SQL that is not a read.** The single-`SELECT` parse and the deny list. A user who wants defence in depth points `how` at a read-only role; setup recommends it.
- **Row values or secrets in a comment.** Comments are built from counts, names and check lines, then passed through the redaction library. Row values never enter the builder.
- **Screenshots with customer data.** Off by default; the opt-in text names the risk and where the files land.
- **Injection from ticket text, pages and query results.** All data. `qa-tester` is read-only and guarded; the only tracker write is the comment the script built, sent by the main thread after the user's answer.
- **Test files in the working tree.** They can break a later `git add -A`. The report and the comment both list them, and `tests-close` proves nothing outside the globs changed.
- **Cost and time.** Browser checks are serial in one pane. Budgets cap checks; the plan shows the count first.
- **Five more uncalibrated questions.** They decide nothing at ship.

## Build order

1. Libraries: environment rule, SQL rule, method choice, coverage, status. Tests.
2. `qa.mjs`: `probe`, `start`, `plan`, state, config precedence. Tests against a temp repo.
3. Running: `run`, `tests-open`/`tests-close`, `browser-record`. Tests with stub commands.
4. Evidence: `post-plan`, `post-record`, `report`, tracker adapters. Tests.
5. Jev questions, case records, `outcome`, `stats`, `calibrate` wiring.
6. `SKILL.md`, `qa-process.md`, `setup.md`, README, manifests, sync tests.
7. One real run on this repo (`checks` only, printed), then one on an app repo with a browser and a posted comment, with approval.

## Verification

```bash
node --test skills/*/scripts/test/*.test.mjs
bash skills/changelog/scripts/test/release-ranges.test.sh
claude plugin validate . --strict
```

Tests that must exist:

- Environment: production host, subdomain of one, wrong kind, empty `production_hosts`, each refused; local allowed.
- SQL: `SELECT`, `WITH … SELECT` accepted; `UPDATE`, two statements, `SELECT … INTO`, `FOR UPDATE`, a denied function, a comment hiding a second statement, each refused; `LIMIT` appended once.
- Config precedence: `qa-this.json` over `wtf.json` over `changelog.json`; `needs: setup` only for what is missing.
- Method choice: each default rule, a path rule, `--method`; an unavailable method reported with its reason; an uncalibrated Jev answer changes nothing.
- Coverage: a criterion with no check is `uncovered`; budgets cut with a count.
- `run`: exit code and tail recorded; a non-zero exit is a failed check; the API verb rule.
- `tests-close`: a new file inside the globs passes; a source file edit is a violation and fails the check.
- `browser-record`: a claimed screenshot that does not exist is dropped; `blocked` handled.
- Every status row. A failed check can never yield `passed`.
- `post-plan`: 12-line cap; no row value and no secret-shaped string in the body; screenshots only when opted in; refused for `post: off` and for an item with no destination.
- `report`: 60-line cap; lists new tests and untested criteria.
- Jev state holds no diff, row value or URL query string.
- `SKILL.md` documents every command, method and status the script emits, and names no tracker write other than the comment and the opt-in attachment.
