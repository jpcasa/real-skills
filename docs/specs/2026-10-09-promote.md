# promote: move what one environment runs to the next one

Date: 2026-10-09 · Branch: `jpcasa/promote-skill-7999e9` · Ships as `/real-skills:promote`, plugin `0.10.0`

## Goal

Add `/real-skills:promote`: learn once how a repo's environments are fed (which branch deploys where, which environment promotes into which), store that next to the other skills' config, and then promote the current state of one environment to the next through a gated flow: preflight, brief, infra and migration check, open the promotion PR, merge it, watch the deploy, verify what is running. A script computes every gate and makes every write; the agent reads, explains and asks.

It sits after `qa-this` and `check-infra-and-migrations`, and before `changelog`.

Model: echo1's repo-local `/promote` (`main` deploys staging on push; a `main → production` PR deploys production). That skill stays where it is and is untouched, as with `wtf`.

## Decisions taken (asked 2026-10-09)

- **Write scope:** opens the promotion PR after one yes and merges after a second, separate yes. The source head is re-verified seconds before the merge. Never `--admin`, never `--auto`, never a ruleset or branch-protection change.
- **Mechanisms in v1:** branch PR only (source branch → environment branch). Anything else is recorded as `manual` and its command is printed, never run.
- **Jev:** shadow. `probe` and code propose the pipeline, the user confirms it once at setup, and Jev's reading is logged next to that answer, so every setup labels its own cases for `/calibrate`.
- **`blocked` from `check-infra-and-migrations`:** stops open and merge. It continues only when the user accepts that blocker in this run, which is recorded. `caution` and `unverified` are shown in the brief and restated at the merge question.

## Non-goals

- Tags, GitHub releases, `workflow_dispatch` and provider commands (`vercel promote`, `render deploy`) as promotion mechanisms. `manual` covers them by printing the command.
- A hotfix lane, freeze windows, PR labels, heads-up messages, ticket status changes. echo1's own skill has these; they are repo rules, not a general flow.
- Running a migration, a repair script, a rollback or a deploy command. The runbook from `check-infra-and-migrations` names them; a person runs them.
- Bypassing anything: admin merge, disabling a ruleset, re-running a failed check until it passes, opening a second promotion PR.
- Hosts other than GitHub.
- New agents. The main thread reads; the script decides.

## Approach

### 1. Commands

```
/real-skills:promote [<env>] [--dry-run] [--no-merge]
/real-skills:promote setup
/real-skills:promote status
/real-skills:promote watch [<run-id>]
```

- `<env>`: the environment to promote **to**. With one promotable environment it may be left out. With more than one it is asked, never picked.
- `--dry-run`: preflight, infra check and brief. No write.
- `--no-merge`: opens the PR and stops. `watch` picks up after a person merges.
- `status`: per stage, what is waiting (commits, PRs), the open promotion PR, the last run.
- `watch`: the deploy and the verification of a run that already merged, or was merged by hand.

### 2. Flow

```
start (stage · range · PRs · gates) ──► nothing to promote ──► stop
        │
        ▼
check-infra-and-migrations on the same range ──► check (verdict read from its harness, same head)
        │                                              │ blocked ──► stop, or accept (per run, recorded)
        ▼
brief in chat ──► YES #1 ──► open (one PR, body = the brief)
        │
        ▼
ready (head unchanged · checks · mergeable) ──► YES #2 ──► merge (--match-head-commit)
        │
        ▼
watch (workflow runs + GitHub deployments for the merge commit) ──► verify (health · running commit)
        │
        ▼
result ──► offer /real-skills:changelog
```

### 3. Config: `.claude/promote.json`, reuse first

```json
{
  "stages": [
    { "env": "staging", "branch": "main", "how": "push", "deploy_workflow": "deploy.yml" },
    { "env": "production", "branch": "production", "how": "pr", "from": "staging", "merge_method": "merge", "production": true }
  ],
  "verify": {
    "production": { "health": "https://app.example.com/api/health", "deployed": "<read-only command that prints the running commit>" }
  },
  "jev": "shadow"
}
```

- `how`: `push` (the environment follows its branch; getting there is an ordinary merge and not this skill's work), `pr` (a PR from the `from` environment's branch into `branch`), `manual` (`command` is shown, never run).
- `merge_method`: `merge` (default), `squash`, `rebase`.
- `deploy_workflow`: optional. On the source stage it is the run `source_deployed` looks for (without it, a successful GitHub deployment of that commit counts); on the target stage it names the run `watch` waits for.
- `verify.<env>.deployed`: a shell string the user wrote. Same boundary as `live` in `check-infra-and-migrations`: write-word guard at config load, runs only after a per-run yes, and the credentials must be read-only because the guard cannot see what a command does. Output must contain the promoted commit (7+ characters) to count as verified.

Read from the other files, never copied: `release` (`changelog.json`, `wtf.json`, `check-infra-and-migrations.json`), `environments`, `production_hosts`, `hosting` (`wtf.json`, `qa-this.json`, `check-infra-and-migrations.json`). With no `stages`, `check-infra-and-migrations.json` `targets` gives branch → environment, and `start` returns `setup` in `needs`.

The other direction: `check-infra-and-migrations` reads `stages` as its `targets` when it has none of its own (both are `{branch, env}`), so one setup answers both.

### 4. Setup and Jev

`probe` reads names only: remote branches, workflow file names with their trigger branches and `environment:` names, hosting files, and whether a branch's first-parent history is made of merges from another long-lived branch. It proposes a pipeline with the evidence for each line. Setup asks one round: is this the pipeline, which environment is production, merge method, optional `verify`.

Three questions, all in `UNCALIBRATED`, one case per candidate:

| Question | Asks | Label | Unsafe side |
|---|---|---|---|
| `branch_deploys_env` | Does a push to this branch deploy this environment? | the confirmed `stages` | none |
| `env_promotes_from` | Is this environment fed by promoting that one? | the confirmed `from` | none |
| `env_is_production` | Is this environment production? | the confirmed `production` | `fn` |

`configured` (called after the file is written) validates it and writes the labels. Switched on by `/calibrate`, the first two change which option setup recommends; `env_is_production` can only add the production wording and never remove it. Nothing here decides a gate.

Sent: branch names, workflow file names, trigger branch names, environment names, hosting file names. Never a URL, a host, a workflow body or an env value. Off: `"jev": "off"` or `PROMOTE_JEV=off`. Catalog 37 → 40.

### 5. Gates (`start`, recomputed by `ready`)

| Gate | Blocks when |
|---|---|
| `range` | Empty: nothing to promote. Ends the run, not an error |
| `merges_cleanly` | `git merge-tree` of target and source conflicts. Not a block but a warning when it merges and the result is not the source tree: the target carries something the source lacks (an unmerged hotfix) |
| `open_pr` | Never blocks. An open PR from the source is reused, never doubled. Another open PR into the target branch is a warning: merging it moves the target under this promotion |
| `source_checks` | A check on the source head failed. Pending: wait. None: `unknown`, said plainly |
| `source_deployed` | `deploy_workflow` is set on the source stage and has no successful run for exactly the source head. Not set and no GitHub deployment of that commit: `unknown` |
| `infra_check` | Verdict `blocked` and not accepted in this run. Sibling skill not installed: `unknown`, said plainly |
| `head_unchanged` (`ready`, `merge`) | The source or the PR head is no longer the commit the brief and the check covered. The run ends; start again |
| `pr_mergeable` (`ready`, `merge`) | GitHub says conflicting, blocked or checks failing. Reported with GitHub's reason; nothing is retried or bypassed |

A gate that could not be read is `unknown`, never `pass`.

### 6. Infra and migrations

`start` calls the sibling harness (`../check-infra-and-migrations/scripts/check.mjs start`) on `<target sha>..<source sha>` with the stage's environment. Nothing bucketed: the gate passes as `nothing_to_check`. Otherwise `start` returns that check run, and the agent follows that skill's own flow for it (live reads question, findings, `record`). `check` then reads the verdict through a new read-only `check.mjs verdict --run <id>` and refuses a verdict whose range is not this promotion's. The agent never reports the verdict itself.

`accept --run <id> --confirmed` records that the user accepted the blockers by name. The brief and the PR body carry the verdict, the blockers in full sentences and the runbook.

### 7. Writes, all through the harness

| Command | Writes | Refuses |
|---|---|---|
| `open --confirmed` | One PR, source → target, body from the brief | A blocking gate, a moved head, `--dry-run`, an existing promotion PR (returned instead) |
| `merge --confirmed` | `gh pr merge <n> --<method> --match-head-commit <sha>` | Anything `ready` refuses, `--no-merge`, a second merge. Never `--admin`, `--auto` or `--delete-branch` |

`--confirmed` means a yes to that action in this conversation. A yes to open is not a yes to merge. On a production stage both questions say "this deploys to production".

### 8. After the merge

`watch --wait <s>` reports workflow runs and GitHub deployment statuses for the merge commit (Vercel and Netlify report through deployments). `verify` runs `health` and, after a yes, `deployed`. Result: `promoted_verified`, `promoted_unverified` (deploy green, running commit not checked), `not_serving` (deploy green, the environment runs another commit), `deploy_failed`, `deploy_pending`. "Deployed" is never said from a green workflow alone.

### 9. State

`~/.claude/state/promote/<run-id>/run.json` (gates, SHAs, PR, confirmations, results), `log.jsonl` (stage, counts, result; no PR text), `jev.jsonl` (cases and labels). Not pruned.

### 10. Changed by the review (2026-10-09)

- `head_unchanged` blocks when the branches cannot be fetched.
- An acceptance covers exactly the blockers read out. The verdict is read again before every write; another list of blockers clears it.
- `check` refuses a verdict recorded for another environment.
- `open` sends only the text `brief` last returned (hash kept in the run), and refuses when it cannot tell whether a promotion PR is already open.
- `watch` counts the stage's `deploy_workflow` and GitHub deployments. Other workflow runs on the commit are not a deploy.
- `source_deployed` by deployment needs one named like the stage; a workflow run needs to be on the source branch.
- `verify.deployed` counts only when the output names the promoted commit and no other, and the command that runs is the one that was shown.
- More checks than one page holds reads as `unknown`.

Left as designed: an `unknown` gate is said and restated, and does not block (except `open_pr` at `open`).

## Rejected alternative

One shared `.claude/real-skills.json` that every skill reads. It is the cleaner single source, but every skill here must work installed as a single folder with its own file, and it would mean migrating five loaders and every existing repo config. The fallback chain already gives "answer once", so `promote.json` joins it.

## Changes outside `skills/promote/`

- `skills/check-infra-and-migrations/scripts/check.mjs`: `verdict` command (read-only). `lib/config.mjs`: `targets` falls back to `promote.json` `stages`. `SKILL.md`, `references/setup.md`: both documented.
- `skills/do-shit/scripts/test/sync.test.mjs`: copy lists, `sets`, count 37 → 40. `skills/calibrate/scripts/lib/catalog.mjs`: three lines. `skills/calibrate/scripts/calibrate.mjs`: `promote` in the list of state folders it reads.
- `README.md`, both `plugin.json` (`0.10.0`, description), both `marketplace.json`.

## Risks

- **A merge into a production branch cannot be taken back.** Two confirmations, `--match-head-commit`, no bypass flags, and a test that neither `SKILL.md` nor the harness contains `--admin`.
- **`verify.deployed` may read production with whatever credentials the user gave it.** Per-run yes, write-word guard, and the setup text says read-only credentials are the real boundary.
- **`watch` depends on the host reporting to GitHub.** No run and no deployment for the merge commit is `deploy_pending` then `unknown` after the wait, never success.
- **Squash-merged promotions** make the next `merge-tree` conflict. That is reported as what it is; the fix (back-merge) is named, not done.
- **Sibling coupling.** A single-folder install, or an older `check.mjs` without `verdict`, gives `infra_check: unknown`.
- **First real merge is unverified until someone promotes with it.** The release note says so.
